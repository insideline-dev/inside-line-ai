## 2. Blockers I hit and how I got past them

### 2.1 Plan mode + nested-agent constraint
Sub-agents spawned via the Agent tool can't easily spawn *their own* sub-agents (advisor/explore). This meant the senior agents I dispatched couldn't self-review through advisor mid-flight. **Workaround**: I ran a single combined advisor pass after each batch of agents returned, on the diff. Caught real bugs (4 of them in the 3-story batch — see commit history of `f90513b`).

### 2.2 `gpt-5.4-mini` false-positive blocker from advisor
Advisor flagged `SCREENING_LENS_MODEL` defaulting to `gpt-5.4-mini` as "not a real model — will 404". **Reality check**: `gpt-5.4-mini` is the repo's standard cheap-tier default; `env.schema.ts` uses it for 7 other AI features (extraction, research, evaluation, etc.). The senior agent correctly matched repo convention. Skipped the "fix"; documented it in the response.

### 2.3 `useTriageDecision` 404 detection by string-matching
Initial deal-card hook detected 404s via `/404|not found|HTTP 4/i` regex on the thrown error message. Fragile — backend's 404 copy could change and the hook would silently turn into an error state. **Fix**: introduced `ApiError` class in `frontend/src/api/client.ts` carrying `response.status`; hook now checks `err.status === 404`. Shipped in `f90513b`.

### 2.4 Lens-key drift in deal card
DealCard hardcoded `LENS_ORDER = ["market", "team", "traction"]`. The triage policy is lens-agnostic, so adding a `gtm` lens later would silently leave the card showing an empty traction tile. **Fix**: drove tile rendering from `decision.lensSnapshot` directly; placeholder `["market", "team", "traction"]` only used for the "not screened yet" empty state.

### 2.5 Policy version drift (DS-E7)
`POLICY_VERSION = 1` and the threshold constants (`LOW_SCORE_THRESHOLD = 40`, `ADVANCE_SCORE_THRESHOLD = 60`) were independent. A future PR could tweak a threshold without bumping the version, silently breaking historical decision interpretability. **Fix**: introduced `POLICY_SNAPSHOT` constant + a snapshot test that locks the tuple. Any threshold change without a `POLICY_VERSION` bump now fails CI.

### 2.6 `usedFallback` heuristic footgun (DS-E10)
Contract builder inferred `usedFallback` from `rationale.toLowerCase().startsWith("lens unavailable")`. That string was duplicated across `base-lens.agent.ts` (writer) and `screening-output.service.ts` (reader). Renaming one would silently flip `usedFallback` to `false` everywhere. **Fix**: extracted `LENS_FALLBACK_RATIONALE_PREFIX` constant from the lens base class; contract builder imports it. Single source of truth, marked with a `TODO(DS-E2-F1-S2)` to replace with a real DB column.

### 2.7 Duplicate render in investor route
Initial deal-card wiring rendered `DealCard` *and* `CardsView` simultaneously when shortlist ≤ 3, so the same startup appeared twice on the page. **Fix**: replaced with `if-else` so DealCards render *instead of* CardsView for short lists.

### 2.8 NestJS DI boot crash (`ScreeningOutputService` re-export)
The frontend agent couldn't run `bun generate:api` because the backend wouldn't boot — `Nest cannot export a provider/module that is not a part of the currently processed module (AiModule). … ScreeningOutputService`. The DS-E10 commit listed `ScreeningOutputService` in `AiModule.exports` but the provider was actually owned by `ContractsModule`. **Fix**: removed the redundant export; `ContractsModule` is already imported and re-exported, so consumers reach the service through the module graph.

### 2.9 Magic-link broken in dev (worked around, NOT solved)
Backend logs show `[EmailService] Failed to send email: Invalid 'from' field`. Backend returns `200` for `POST /auth/magic-link/request` but no email reaches the inbox. Could not perform real-data browser E2E for DS-E6 or DS-E3. **Workaround**: enabled `VITE_MOCK_AUTH=true`, captured static UI screenshots, reverted env. The generating banner with live sub-step animation and the populated-after-WS-event states are NOT screenshotted.

### 2.10 `phase-transition.service.spec.ts` and `investor.controller.spec.ts` pre-existing failures
Both have failing tests on `main` *before* any of today's work (verified via `git stash`). 24 tests in `investor.controller.spec.ts` failing on a `StartupMatchingPipelineService` DI gap; 6 in `phase-transition.service.spec.ts` failing on a fixture missing `CLASSIFICATION` from `state.phases`. **Decision**: left as-is, called out in commit messages and review notes. Separate cleanup ticket needed.

### 2.11 `git add -p` non-interactive failure when committing today's work
The repo's CLAUDE.md forbids `-i` flags, and `-p` interactive partial staging didn't run cleanly via heredoc input. Result: I couldn't cleanly split a single file's diff between two commits (env files mixed log-retention pre-existing work with today's screening additions). **Fix**: shipped pre-existing log-retention work as one precommit using whole-file staging on the unrelated files (`app-file-logger.ts`, `sweep-old-logs.ts`, `docker-compose.yml`); env files containing both LOG_RETENTION_DAYS and SCREENING_LENS_MODEL got committed with the lens story. Clean attribution per file group; messy per line.

### 2.12 Drizzle `_journal.json` cumulative across 3 migrations
`_journal.json` accumulates entries for every migration. All 3 of today's migrations (0011/0012/0013) wanted the same file. **Fix**: committed the full final journal with the first migration commit (DS-E2-F1-S1 lens). Subsequent migration commits don't touch the journal. Intermediate commits have a journal pointing at not-yet-existent SQL files — harmless for local history, would break a `checkout middle commit && db:migrate` flow.
